# 目录架构与脚本位置

在文档/接口设计前确定代码归属。先查项目真实结构与相关框架文档；只核对相关目录，不重建全工程。用户未授权搬迁时只记录现有位置与必要新增位置，不移动旧代码或生成目录。

## 先定目录，再定脚本

在模块文档增加“## 目录架构与脚本位置”，给一棵本模块实际或拟定目录树（设计态注明拟定），以及下表。路径相对代码仓库，符合真实命名空间/package/module 规则；只写本次相关文件。

| 类/模块 | 角色 | 代码文件路径 | 命名空间/模块 | 放置理由与装配者 |
| --- | --- | --- | --- | --- |

调度器放实际模块入口/编排层，执行者放同模块实际规则/命令/策略层，工具放真实复用范围内的工具位置，数据放实际契约/配置/模型层。沿用已有文件夹，项目未有 Executor/Tool/Data 子目录时不强造整套空层级；跨模块真正共享的内容才放 shared/Common，不能为复用方便移动状态所有权。

客户端、服务端和真实共享边界写清楚；自动生成源码/API 与手写脚本分开。类名、文件名、文档名与图节点名按现有规范对应。没有类的语言按实际模块/函数文件组织，不假装每个脚本都是 C#。

UI 沿用 [UI 规划](ui.md)：客户端执行业务在模块 View/view，服务端执行业务的客户端 UI 直接在对应模块根；资源/生成绑定的位置按实际框架。指出谁注册/创建/持有每个入口，而不仅画文件树。

## 已实现与拟定

设计态列拟定路径和依赖接口，不写内部算法；源码 sources 只列真实证据，尚未存在路径由目录表/API Source 明确拟定。现状模式按真实实现说明路径；架构图和脚本表同步，不能用旧规划代替当前代码位置。

API 声明在独立 docs 的 api/，不是生产脚本位置；原语言代码 API 不参与编译/发布。临时扫描/验证脚本放仓库外或精确本地忽略，正式可复用技能工具放本技能 scripts/，测试代码不分发到技能。

## 独立目录架构文件

另外生成 `docs/文档/目录架构.md`（设计态放在对应文档输出根），使用 [目录架构模板](../../assets/templates/directory-architecture.md)，并由该文档根 README 链接。该文件集中展示本次系统的文件夹层级、client/server/shared 归属、真实或拟定脚本路径及对应类文档跳转；API 文档与生产脚本分别列树，自动生成内容明确标注。大型项目只展示相关系统，不扫描或抄录无关完整工程。它是目录导航，不复制类职责、流程图、API 签名或测试记录；各类文档现有结构继续保留。

新开发先完成文档与此目录架构，再由规划读取这些文档建立逐类执行任务；规划不复制目录树，也不自定第二份脚本位置。实现时路径改变，同步此 MD 与相关类文档。

文件放置固定为同级 `README.md` 与 `目录架构.md`。现状入口为 docs/文档/README.md，因此目录架构在 docs/文档/目录架构.md；设计态入口为 docs/文档/<模块>/设计/<任务>/README.md，因此目录架构在该目录下。入口“目录架构”一项必须直接链接该文件；不能只在职责子目录里画树而省略这份总层级文件。

按 [模块文档目录](../contracts/module-layout.md) 生成总层级与各模块层级：docs/文档/目录架构.md 对应总入口，docs/文档/<模块>/目录架构.md 对应模块入口。职责/API/专题均归模块内部，不再聚集在根的职责/api 目录。
