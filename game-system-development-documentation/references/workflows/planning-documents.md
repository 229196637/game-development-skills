# 规划文档生成

可直接调用文档技能，或由 game-system-development-planning 在研究代码与需求后传入需求、范围、已有决定及文档模式。文档技能负责生成和同步产物，不创建或排序 TODO；完成后把模块依赖、交付门槛和未决项返回当前调用者；只有调用者正在编写规划时才交回规划技能。已实现补录/更新也可单独调用本技能的现状模式；文档任务不必创建执行工单。

## 操作顺序

1. 先按 [独立文档 Git](../contracts/docs-git.md) 确认本次 docs 是独立仓库，再读取已有系统 Markdown/API、项目指令和用户已确认需求。已有资料足够且未过期不重复扫描，缺失或冲突才核对相关实现。
2. 按 [已有框架能力与重写选择](framework-reuse.md) 给具体能力、实际接口和差距；沿用已确认决定，未确定的替代设计不继续。任务 README 记录框架与类索引。
3. 先完成 [目录架构与脚本位置](script-layout.md)：复用实际框架目录，确定各角色的源码路径、归属、命名空间和装配/调用关系，再设计接口。不能先写完类再猜文件放哪。
4. 用 [规划目录与元数据](../contracts/planning-layout.md) 在任务内生成职责/接口/关系文档及Markdown planned/mixed API；角色与调度流水线使用 [调度器与执行者](dispatchers.md)，图与接口遵守 [模块图规范](module-diagrams.md)。不写算法/实现伪代码，不把拟定能力称已实现。
5. UI 需要时按 [UI 规划](ui.md) 给独立 MD 和 HTML；配置调用游戏 Excel 配置表技能，网络需要独立专题。所有创建目录给摘要 README，API 目录 README 只导航，不代替具体 API Markdown。
6. 用 documentation_tool.py check <文档目标> --mode planning 检查文档及引用，把目录/类路径、模块开发前置、交付条件、框架决定和阻塞返回当前调用者。规划调用者随后建立同层级同类名工单并给出依赖顺序，不自动执行；独立文档任务到此交付。实现后由当前执行者调用现状模式同步文档与已实现 API，不反调规划。

## 产物所有权

本技能维护两种文档：设计态在 docs/文档/<模块>/设计/<任务>/，现状在 docs/文档/<模块>/职责 与 api；状态、版本和来源如实区分。模块与设计 README 只维护文档导航，执行工单与顺序在 docs/规划 中由规划技能维护，不覆盖用户已有工作项或证据。目录/职责/API/流水线关系变更后返回当前调用者；仅已有执行工单确实受影响时，由当前调用者进入规划修订对应工单，独立文档任务不因此创建或重启规划。

仅设计调用无需擅自改生产代码；开发、测试、验收仍按任务已有授权，由执行者协调项目对应能力；规划技能只维护规划，不代替执行。

新执行规划只引用这里生成的设计资料，按类记录目标、任务与测试；设计资料和执行任务必须分别存储，不能写入同一个任务根。
