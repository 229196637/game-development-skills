# 老工程扫描
每个扫描模块同时补齐实际依赖架构图和关键流程图，按需要增加时序/状态图；依据 [模块图规范](../../../game-system-development-planning/references/workflows/module-diagrams.md) 与实际实现绘制，未经验证的动态路径明确标注。
1. 盘点源码根、工程文件、入口、模块注册、端/层边界、已有文档和生成目录，明确扫描范围。只读取第三方/生成代码作为依赖证据。
2. 从初始化、外部调用与事件订阅追踪真实调用链，按状态所有权与职责确认系统边界，不单凭文件夹名称分系统。边界不确定时先记录已确认关系。
3. 为每个系统记录源文件、真实命名空间/类、公开 API、数据流、状态修改者、依赖、释放与失败分支；找调用示例和相关测试。
4. 生成每系统说明与 API 快照，正文中的每个关键事实对应源文件或实际验证。文档缺失不需要先补规划，也不把现有实现包装为未来设计。
5. 更新分类和根索引，核查 meta、相对链接及快照排除编译。一次专项扫描可逐系统交付；明确未扫描、未验证及过期范围，不能部分扫描却声称全项目覆盖。

静态阅读只能证明读到的代码路径。未运行的流程写“静态核对”；动态行为结论必须附真实验证方式与结果。工程缺乏测试时给可复现检查步骤，不凭空写“测试通过”。
