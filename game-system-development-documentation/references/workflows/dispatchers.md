# 调度器与执行者

有调度职责时使用本规范；不因名称包含 System 就认定它是调度器。调度器决定顺序、分派、时间推进或协调结果；执行者完成被分派的动作或条件判断。一个类可兼有两种职责，按实际入口说明。规划描述已确认设计并标拟定；正式文档只记已实现事实，不凭空改架构。

## 调度器文档与 meta

每个调度器有直接可链接的 Markdown 入口。现有系统主体只有一个调度器时就在主体说明；多个调度器分别放系统目录下独立 MD，主体只导航，不复制内容。规划放本任务模块内的调度器 MD，任务和模块入口链接它；不为一个调度器重建整套规划文件。类文档文件名用实际类简单名（例如 GameRuleSystem.md），一级标题用相同类名，meta.dispatcher 与图中该类节点第一行也一致；不使用 game-rule.md 之类别名。跨语言函数模块按实际模块名命名，不造类。改名时同步所有引用。

保留所属技能的基础 meta，类型/模块说明必须用 roles 标记角色，仅调度器再加 dispatcher 与 design_patterns：

~~~yaml
roles: [dispatcher]
dispatcher: GameRuleSystem
design_patterns:
- name: 策略模式
  uses: 按规则类型选择 GameRuleStep 派生实例，通过统一接口判断各类完成条件
- name: 队列化事件分派
  uses: 信号先入队再消费，避免子模块回调递归推进规则
~~~

name 可写真实设计模式或编排机制；uses 指明参与类型和具体用途。不要堆模式名或强套命令、责任链、状态机：顺序规则不等于责任链，没有 Execute/命令封装也不能仅因名称叫 Step 就认作命令模式。拟定模式说明拟定，开发后据实现更新。无经典模式时可记录“顺序调度”等真实机制。执行者不强制重复写模式 meta。

正式文档的跨调度器依赖用现有 dependencies/document/uses；规划文档用现有 links 映射调度器文档，并在交互正文说明用途。不新增 communication manifest 或全量调用清单。

## 每条调度流水线的图

调度器正文使用 `## 调度流水线`，下面每条主要流水线用 `### <名称>`；流水线标题就是这条图的名称；引用它的节点首行使用同一名称。每条标题后、图之前写一两句“用途：……”：说明这条链做什么、由什么触发及完成什么交接，再画自己的 Mermaid flowchart，不能只有图或只有约束说明。按实际入口划分，例如启动、Tick、规则推进、信号消费、停止；不同入口有不同分支/顺序就分图，同一链上的小动作无需另起流水线。

图画触发者 → 调度器入口 → 对应执行者/其他调度器 → 完成、拒绝或退出；标清同步调用、排队、回调、有效帧及返回。循环标退出条件，真实存在的死亡优先、取消、重复请求和失败边界放在相关图中。每条图旁用一两句话说明入口、顺序和结果，不复制方法体。Tick 与规则推动等不同链不能混成一条无标签长线。

跨调度器通信必须在参与的流水线图显示发送和接收方向、实际接口/信号及交接时机；回调入队与后续消费要区分，双向通信分别画边。外部调度器节点使用 Mermaid `click Node "relative.md#流水线锚点"`，并在图下给同目标 Markdown 链接。同一调度器内流水线互相调用/交接时也必须跳转：节点第一行用目标流水线标题，click 到本文件 #流水线锚点，并在图下附同目标普通链接；只是执行普通动作的节点不强行创建流水线。跨调度器有明确接收流水线时跳到其锚点，不只停在文档顶部。目标 MD 的实际标题/锚点必须存在；未确认接线不能画成已实现。含括号等特殊字符的边标签加引号，实际渲染检查 Mermaid 语法。图保持 18～20px，实际预览不小于约 16px；复杂图拆开仍保留跨图跳转。

## 角色分类

roles 使用非空列表：dispatcher（调度器）、executor（执行者）、tool（工具）、data（数据）。按当前实际职责填写，兼任时列多个值并说明对应入口。规划索引/纯导航文件无需角色标签，具体类型/模块规划和正式主体必须标记；规划时为拟定角色，开发后同步。

工具提供复用的计算、转换或查询，不拥有流水线调度权限；常见 static 类说明实际静态入口，但非静态工具也可以标 tool，静态调度类仍标 dispatcher。工具文档简述用途、输入/输出、真实副作用与 API 即可，不强制调度图或长生命周期。executor/tool 的独立短文档不强制架构图。

## 数据

数据用 roles: [data] 表示配置、上下文、请求、快照、结果等实际数据类型。简述字段/结构的业务含义、来源、谁创建/修改、谁读取，以及共享/复制/不可变的真实契约；不写执行流程或调度权限。仅维护必要说明，不为每个字段再建文件。公开函数 API 规则不变，不能为了记录数据字段把属性/字段塞进公开函数声明。

数据与工具、执行者的独立短文档不强制架构/调度图。复杂数据关系需要时才画；字段详细配置字典仍按配置技能。记录消息转交、事件接线和回调时机时直接画在相关调度器通信图或使用说明中，不另设角色。

## 执行者只说明执行内容

用短列表或小表列执行者类型和“执行什么”；确需查阅时直接链接 API。只补会影响调用的输入、完成信号或释放归属，不为每个执行者复制调度图、模式说明、整套生命周期和文件树。执行者不能被描述成拥有调度器的排序、时间推进或终局权限。

例如 GameRuleStep 的派生类分别累计事件、判断有效生存时间、等待目标 Boss 的真实死亡；GameRuleSystem 决定激活、推进、释放和终局。实际项目名字优先，不改成示例中的 GameStep。

## 同步与检查

入口、模式、流水线顺序或跨调度器接口变化时，同步 meta、图、跳转目标与 API。结构工具检查新增 meta、各流水线图及跨调度器文档跳转；实际通信与执行顺序仍对照接口或源码核对。只查已有足够 API 时不扩大扫描。测试/验收记录放任务验证文件或独立报告，不放正式文档正文。
