# 正式文档边界
正式系统文档是给调用者和维护者阅读的使用说明。按实际实现重新组织，每系统一份主体 `docs/文档/systems/<模块>.md`；规划、任务 TODO、测试报告各归原位置。不要按扫描顺序写，也不要把每个检查项变成章节。

## SDK 式系统说明
参考项目 `docs/sdk/systems/` 的实际写法，而不是套用固定资料表：

- `scenesystem.md`：先解释场景概念，再按获取、加载、切换、卸载等使用场景介绍调用与边界。
- `disposableobjectsystem.md`：围绕普通销毁、宿主级销毁和扩展场景讲清持有与清理语义，把限制放在相应操作旁。
- `loadinguiscreen.md`：先按需求选择入口，再给最短用法和需要时才看的扩展细节。
- `messagingsystem.md`：按发送/接收和客户端/服务端区分示例，帮助读者找到自己的调用场景。

这些是写法参考，不是可照搬的业务或 API 清单。项目有 SDK 时先读与本模块最相关的一两份系统文档；没有 SDK 时采用下面的组织原则，不要求复制或安装 SDK。SDK 的字段/API 全量清单、相关文档列表不照搬：本技能仍仅在独立 API 文件收录公开函数，文档依赖仍放 meta。

正文围绕以下阅读路径组织，标题按模块业务命名，允许合并、调整顺序：

1. **用途与入口**：开头一两段说明解决什么问题、在哪一端、谁调用。存在多个真实入口时用小表帮助选择；只有一个入口不造选择表。
2. **理解系统**：必要概念、实际架构图、模块分工。图只画本系统关键参与者和实际边，节点说明持有/调用/通知含义；不堆全部类、方法或文件树。
3. **基本用法**：给最常用操作的最短真实调用示例，先说前置条件，示例后说明成功的含义。依次能看懂如何接入、调用和结束使用。无需在此展开全部重载。
4. **具体使用场景**：确有不同用法时按行为拆小节，例如“加载关卡”“切换玩家”“退出时释放”，每节只讲该操作的条件、短示例和限制。不是机械的“职责/接口/关系/流程/验收”六件套。
5. **生命周期与持有关系**：保留初始化、就绪及释放的真实契约；简单系统几段话即可，多对象确需比较时才用表。可集中说明共用契约，操作特有的取消/失败/借用限制就近说明，避免重复。
6. **API 入口**：直接链接端/模块下的原语言声明。少量文件用链接，多端多类型才用映射表。详细签名和完整参数/返回/异常注释由 API 承担。

“基本用法”是已存在公开接口的调用示例，允许有短调用代码，不是内部实现或伪代码。按项目实际语言写，实际类型、上下文、端归属与执行阶段必须可确认。省略接线要明确说明示例所在上下文及变量来源，不造辅助函数或用虚构 API 填空；条件不完整时先补查证据。不要把声明文件全文贴进正文，也不要用禁止实现体的 API 规则禁止正文调用示例。

常见误用只收真实会影响调用的情况，可放相关操作旁；确有多个需要集中查找时再列小表。没有内容的“核心概念”“常见错误”“高级用法”直接删掉。一个事实只在最适合查阅的位置完整说明；主体保留必要调用提醒，专题/API 承担细节。

正文默认只保留实际架构图，不强制流程、时序、状态图。生命周期用真实顺序说明即可。其他系统文档路径与依赖用途只在 meta.dependencies 维护，不重复依赖表、依赖版本表或“相关系统”章节。正文可以说明依赖能力如何参与当前操作，但不再复制一遍依赖目录。

# 精简 meta
正式系统说明默认仅用以下关键信息：
~~~yaml
---
system: <模块标识>
side: [client] # 实际 client/server/shared，可多端；shared 必须真实共享
updated: '<YYYY-MM-DD HH:mm:ss ±HH:MM>'
code_revision: working-tree # 实际提交；未提交时明确写 working-tree
sources:
- <相对代码仓库根的模块入口或关键源文件>
dependencies:
- document: <相对当前 MD 的其他系统文档>
  uses: <具体依赖用途或所用能力>
---
~~~
sources 只列能定位该系统和关键行为的源码，不写生成源码/扫描文件的全量清单。dependencies 只列真实依赖，不将所有相关文档、上游消费者、索引、API 或规划都塞进去；没有依赖用 []。上游 caller 在架构图/职责里说明，不伪装为下游依赖。

不默认生成 id、kind、title、links、layout_version、schema_version、category、scan_scope、api_files、function_count、code_dirty、verified_by 长列表或多层 metadata：系统由路径/system 定位，标题由正文承担，API 映射仅在正文维护，依赖只在 dependencies 维护。仅真实工具必需的额外字段可保留，并说明理由，不为了兼容模板继续堆字段。已有依赖版本仅在确有版本锁定消费要求时保留。

正式主体不放测试/验收章节或任何执行总结，包括一段简短测试说明。测试方案、用例、执行命令/结果、日志截图、扫描/实验记录均在任务的 verification.md 或既有独立测试报告保存；没有任务规划时沿用项目测试报告位置，不为此补造规划。测试报告不是系统依赖，不塞进 dependencies。已实现功能的真实限制仍写在相应生命周期/API 使用约束中，不与测试缺口混淆。文档需独立版本号时可加 version；没有真实需要不编造。API 文件仍按原语言头注释保留来源、版本/日期与签名/契约静态核对信息；不在 API 文件复制测试记录。SKILL.md 保持标准技能 frontmatter，不采用上述产物格式。

# API 与查询
API 先分 client/server/shared，再按模块：docs/文档/api/<端>/<模块>/<类型或模块>.<原语言声明扩展名>。shared 仅真实共享；模块目录仅存公开函数声明，不另建 MD、manifest 或 meta。主体正文用简短表格/链接直接映射实际命名空间、类型和 API 文件，详细签名及完整契约不再复制进正文；正文保留可照用的短调用示例和当前操作必需的契约提醒。没有公开函数则说明，不建空文件。

已实现 API 足以回答且未过期时不扫描源码。缺失、冲突或需核对当前变更时查看相关实现。规划的 planned/mixed API 仍在任务目录；逐文件核对完成后移动到正式目录并修复引用，不保留双份声明。移动 API 不是复制规划正文。

# 精简后的信息完整性
精简的是重复结构和规划内容，不是关键行为。交付前对照实现确认：初始化前置、状态/对象 owner、owned 与 borrowed、返回成功的真实含义、重复调用、取消/失败及释放顺序均能从主体和 API 找到。细节可放 API 或独立专题，但必须有直接入口；不能用“详见 API”指向遗漏这些契约的旧声明。

不能将内部 owned 集合等同底层资源的完整所有权；Dispose 的实际保留、不重试、部分清理或其他限制照实保留，不用笼统“释放全部资源”替代。文档只记录边界，不擅自修复生产实现。

# 生命周期与持有关系
记录模块由谁创建/注册、何时就绪、如何运行/暂停、怎样关闭/释放。明确依赖的创建先后与释放先后；借用对象不得由模块释放，拥有对象标明唯一销毁者。只写真实存在的阶段，无暂停能力就不添加暂停章节。

用自然段说明实际类或模块的创建/持有者、拥有或借用、状态修改者及释放方，以及订阅/回调与资源解绑；对象较多且需对比时再用职责/所有权表。需要时补取消/失败部分装配、缓存重开、晚到回调等实际边界，不能虚构兜底能力。

# UI、配置及网络专题
需要 UI 时系统主体链接独立 docs/文档/systems/<模块>/ui.md 及其 HTML 设计稿；ui.md 只写实际目录、界面状态/接口、资源绑定和生命周期，不复制规划稿或强制绘制交互流程图。沿用已确认的客户端逻辑 View/view、服务端逻辑客户端模块根目录规则。

Excel 字段字典或网络事件等确需独立查阅时用独立专题，主体只给入口和必要约束，不复制全量字典/协议/验收。专题也用精简 meta，依赖放 dependencies；HTML 无 YAML。已确认设计与实际实现差异只在确有必要时简要说明。

索引只导航；主体不复制任务 TODO、历史修订、规划推演、拟定接口、伪代码和验收矩阵。所有相对依赖/专题/API 链接必须可跳转。迁移已有格式前检查引用和工具消费，只整理本次授权的文件。

## 可读更新时间
updated 与 API Updated 使用 YYYY-MM-DD HH:mm:ss ±HH:MM，例如 '2026-10-12 17:19:55 +08:00'。使用用户时区并注明 UTC 偏移，YAML 使用带引号字符串。修改文件时取本次真实更新时间；历史仅有日期不填猜测时分秒，也不统一补成 00:00:00。历史记录不自动迁移，日期缺少时间的当前产物会由工具指出，实际更新再补真实时间。
