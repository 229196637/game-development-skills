# 测试与交付

按工单 required_tests 与预定验收标准执行有意义的验证，遵守项目构建、模块测试、集成/游戏验证要求；不要只测脚本结构。涉及客户端/服务端项目的必要双端构建也要做，环境无法满足写 failed/not-run 并阻塞。

优先用 run-test 运行实际命令，自动记录退出码、时间、命令参数、工作目录、代码版本与独立 Markdown/完整日志。退出码为零只说明该命令成功，须核对测试数量、覆盖与预期。交互验证或外部系统已执行测试用 record-test 链接已存在的真实报告。失败记录保留；修复后重跑受影响测试，再追加新结果。源码变化后旧结果不能冒充当前版本，先退回受影响工作项以使旧结果失效。

逐项 record-acceptance，填写实际观察、结果及证据。按用户要求的人工验收才需要人类确认，不自动新增审批。实现勾选、测试 passed、验收 passed 是三个不同动作。

## 多媒体验收证据

`record-acceptance --evidence` 保持非空自由单行文字，不要求结构化对象；可在一句文字中用空格分隔多个标准 Markdown 链接：图片用 `![说明](路径)`，视频和报告用 `[说明](路径)`。仍写入原验收证据单元格，不新增字段或列，不改变测试七列、验收五列及工单八 key schema。

- 按验收对象取证：截图验证视觉效果，视频验证动态流程，数值/日志验证内部逻辑；按需组合，不强制全部录视频。证据须对应当前版本的实际观察，不能只凭素材存在判 passed。
- 截图、视频、报告及日志统一放 `docs/测试/<任务>/` 或项目已有独立报告目录，不放工单根或正式系统文档。记录只引用文件，不内嵌 base64、二进制或 GenUI 树。
- 新证据链接的相对路径以**工单文件所在目录**为基准；报告内的相对链接以**报告所在目录**为基准。现有 `--report` 仍由工具解析并记录绝对路径，历史记录不改写，也不重新解释历史相对报告路径。
- 保持单行且避免裸管道字符 `|`；工具写表格时会转为 `&#124;`，手写表格也须转义以免拆列。路径有空格或特殊字符时使用兼容的 URL 编码，示例直接选无空格、无管道路径。

单行例子（沿用 [执行工具](../tooling.md) 的 `$m_tool`、`$m_entry`；已由 developer-1 领取 store，验收 ID 为 contract，实际观察确已通过且文件已存在时才登记）：假设工单为 `docs/规划/背包任务/inventory/职责/ItemStore.md`，下列相对链接均指向 `docs/测试/背包任务/`。

```powershell
python $m_tool record-acceptance --entry $m_entry --id store --owner developer-1 --acceptance-id contract --actual "视觉、动态流程与数量日志符合验收条件" --result passed --evidence "当前版本实测 ![界面截图](../../../../测试/背包任务/screen.png) [流程视频](../../../../测试/背包任务/flow.mp4) [验收报告](../../../../测试/背包任务/report.md)"
```

链接可读、图片/视频可预览或报告存在均不等于 passed；UI 只做只读展示/预览，不走模型、不替执行者判定或回写。owner、依赖、按追加顺序选最新记录及 complete 完成门禁保持不变。

## 完成与交付

调用文档技能同步实际 Markdown API、职责、生命周期和目录差异：API 保持原语言签名与必要使用信息的简洁速查，行为/生命周期/协作详情留在职责并互链；不把测试内容写入正式文档。完成前检查最新报告对应当前代码、报告文件确实存在、必需验证都运行、前置已完成；再 complete。工具只验证登记状态/报告存在，不证明业务正确性或报告诚实。

交付完成/阻塞清单、代码改动、真实测试数量与结果、报告位置、未解决限制。代码与 docs 各在所属 Git 中处理，只在用户已授权范围提交/推送。跨类集成测试可引用同一真实报告，避免复制日志；测试报告不属于正式系统文档。
