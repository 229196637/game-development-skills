# 每个模块必须有图
每个任务下的模块目录必须包含：
- architecture.md 中的依赖架构图：本模块内部职责、实际或拟定类型、上游调用方、下游服务、配置/状态所有者、client/server/shared 边界。
- flows.md 中的关键流程图：各主要入口从触发到结果的流程、参与接口、状态转换和实际需要的分支。异步、多端、多模块消息协作另配时序图；重要多状态生命周期按需要增加状态图。

使用 Markdown 内 Mermaid，图就在对应模块文件中，不只画任务级总图，也不只留文字占位。简单模块图可以小，但每个模块都需要自己的架构图与关键流程图。只有相关结构复杂时才细拆，不把同一张总图复制到各模块。

# 架构图怎么画
节点对应真实或明确标为拟定的模块/类/接口/配置；箭头必须标明调用、订阅、消息、读取配置等关系，约定箭头从使用方指向提供方，不与数据流混淆。不同关系写图例；双向交换分别画方向，不用模糊无标签箭头。
用 subgraph 划分模块和端，显示状态/权威归属；外部系统只保留当前模块真实依赖的接口边界，不扩展全项目。共享接口不表示共享运行时状态。
图旁提供节点与接口/API 文件映射和重要约束；沿用接口文档，图里不另造签名。未确认依赖标待确认，拟定节点标 planned，不能冒充现状。

# 流程图怎么画
按已确认业务和调用契约描述：触发/输入 → 边界校验或调用前提 → 依赖接口调用/状态交接 → 结果或事件。具体到谁执行、调用哪个接口、何时发生和预期结果。
覆盖流程实际存在的成功、失败、拒绝、取消、重入、资源释放等分支；只有该流程确有对应情况时才画，不凭空加防御逻辑。循环和重试注明退出条件，异步注明等待、完成和取消归属。
规划阶段用拟定业务规则、接口顺序、责任和状态来细化流程，不画内部算法、逐行伪代码或函数体。不确定分支注明待确认。实现后按真实代码更新行为及分支。
每条关键流程链接其入口 API、对应任务 TODO 和 verification.md 的验收场景；不需给每个简单辅助函数单独画图。

# 图表可读性
默认优先 flowchart TD/TB。多个端或多个阶段串成横向长图时，按端/职责/阶段拆成几张图，再用独立小图或正文明确保留跨图关系；不能为放大删掉依赖或分支。每个节点只保留名称与核心职责，用换行压缩长标签，细节放图旁表格。
默认 Mermaid 字号 18～20px；在常用文档预览宽度下核对实际显示，不只设置源字号后任由整图缩小。正文阅读时图中文字应至少约 16px；超宽或过密时先拆图、改纵向并精简标签，再调整字号/间距。复杂时序图可按连续阶段拆分，标清前后衔接及原有消息顺序。
必须按文档实际显示宽度检查渲染，不能以 SVG 在无限画布上可读作为通过。只有真正渲染检查后才报告已验证可读；没有渲染工具时说明未验证显示。

# 同步和验收
开发中接口、依赖、状态或消息顺序变化时同步架构图、流程/时序图、正文、API 映射及验收场景。正式系统 Markdown 按文档技能的精简规范保留当前实际架构图，不要求复制规划流程/时序/状态图；规划图标明原设计与实际偏离，链接现状图，不假装设计一直未变。
老工程补文档转文档技能，以实际架构、生命周期、持有关系与 API 提炼，默认只保留架构图；静态阅读不确定的行为标明未验证。
检查 Mermaid 语法、节点/边标签、端归属和分支是否与契约一致。环境有 Mermaid 预览/渲染器时确认可渲染；不可用时仅报告源码检查，不能声称已渲染。验收核对流程场景与测试证据，不以图存在代替运行验证。
