# 任务路由与执行

## 文档是前置

先读取 `docs/文档/README.md`，再读 `<模块>/README.md`、与模块入口同级的 `目录架构.md`、本模块类 MD 和它直接映射的原语言 API；已有有效资料足够就不扫描源码。设计态资料必须明确拟定接口与路径，不当成现成实现。文档缺失/冲突时调用文档技能补齐；规划不承载这些文档内容。现有设计态文档的实际位置可沿入口读取，执行任务另建任务目录，不能覆盖旧设计资料。

用户已认可的文档风格、角色、流水线、客户端/服务端/shared、网络/UI/配置规范继续由文档技能维护。本技能记录“实现哪一项”，不重新定义“系统是什么”。

## 任务目录和顺序

```text
docs/文档/                       docs/规划/<任务>/
  README.md                        README.md
  <模块>/                          <模块>/
    README.md                        README.md
    职责/                            职责/
      README.md                        README.md
      <类名>.md                        <类名>.md
```

相对文档根的职责类 MD 路径必须一致；已有职责子目录也原样镜像。API、目录架构及专题通过工单索引查阅文档，不复制到规划。

每类任务文件名与实际类/脚本名对应，用稳定 task_id 标识任务；同类不同开发任务分属不同任务目录。README 链接文档入口、目录架构和任务；写清“先谁、再谁、最后谁”及必要理由，不复制类索引/职责/API或任务状态。

将文档依赖转为开发前置：契约/数据先于消费者，提供者先于接入，集成先于相关验证。已有能力可作为已满足前提链接原文档，不安排重写。每类 meta.depends_on 只记录本任务的前置 task_id；工具按这些前置排序，未知 ID/循环阻止执行。跨系统双向运行时通信不直接当成开发循环；有真实循环则先明确可交付的契约或记录待确认。用户指定优先顺序不得越过未满足前置；无依赖的任务按入口约定安排。

## 逐类闭环

1. 读取任务关联文档及必需 API；确认目标、接口、路径和前置已满足。框架复用选择按技能入口处理。
2. 用工具建立内容完整的类工单：目标、当前情况与具体改动、文档索引、可核验工作项、验收标准；登记必需测试与验收 ID。测试计划针对公开行为与实际风险，不机械写镜像测试。
3. 首次写业务代码前运行工具 check/list，检查前置完成，将状态改 doing；按文档实现代码。遇到设计变更先同步文档，再更新任务，不在任务正文写替代设计。
4. 执行适用项目要求的构建、模块/集成/游戏验证。把实际命令或复现步骤、预期、实际、结果、证据追加到本类底部测试过程；按预定标准单独追加验收情况。未运行写 not-run，失败写 failed；修复后重跑并追加，保留历史。
5. 完成勾选项，调用文档技能同步实现导致的差异；有后续代码变化时重跑受影响测试，记录当前版本的结果。人工验收只有用户要求时才作为门槛。
6. 工具 complete 检查前置、勾选项及每个必需测试和验收最近记录全部通过，才设置 completed。缺少环境或失败不标完成；明确阻塞原因后记录 blocked，继续不受其影响的任务。

测试记录是执行者提交的证据，工具不会验证命令实际执行或业务正确性。交付前核对证据与当前代码版本；不以工具通过替代真实测试。跨类/系统测试可把同一独立报告链接到相关类底部，避免复制大段日志。
