# 统一入口与路由
每个开发任务以 docs/规划/<任务>/README.md 为独立入口；从这里读取当前任务详细需求、模块关系、TODO、优先级及测试验收。详细内容和所属模块规划均在该任务目录内保存，不散放在项目总索引。docs/README.md、docs/规划/README.md 或已有索引只链接任务，不作为任务执行入口。
游戏开发以 game-system-development-planning 组织任务，涉及配置时调用 game-excel-config，查阅/同步文档时调用 game-system-development-documentation；仅补文档的任务可以直接使用文档技能。按项目现有客户端、服务端、UI、测试技能处理实际领域，只有确实相关时加载。路由是职责划分，不自动授权多代理、创建聊天或并行写文件。

# 多系统任务
一个任务只维护一份总规划，位置 docs/规划/<任务>/README.md，连接该任务目录下各模块文件。详细保存任务背景、已确认需求、目标与预期结果、范围、约束、共享接口、依赖关系、优先级理由、TODO 和测试验收；过长的专题可拆为同目录 Markdown，并由任务入口链接。不同任务分别建文件夹，不将其模块规划混入同一目录。
| 系统 | client/server/shared | 提供接口 | 消费接口/上游依赖 | 规划与系统文档 |
| --- | --- | --- | --- | --- |
共享契约由明确的所有者维护；调用方链接该声明，不复制另一份签名。接口变化及时更新消费系统的关系、TODO 和验证范围。依赖循环先明确真实调用与状态所有权，再在规划中解决或标待确认，不盲目启动相互阻塞的实现。

# 最后根据依赖生成 TODO
先完成模块职责、公开接口、配置/UI/网络和调度通信的规划，确认各模块提供什么、消费什么及交付前提，最后再生成/重排任务入口的唯一 TODO。初期可以登记候选工作，但不能在模块依赖尚未明确时把临时排列当作最终执行顺序。

## 依赖转成开发前置
把模块关系转成具体工作项依赖：提供方的契约/能力先于消费者接入；消费者所需的配置或数据先于读取；集成先于跨系统测试，测试与文档同步先于整体验收。已有且满足本次需求的提供方标为已具备前提并链接现状，不创建“重新开发”任务。

区分运行时调用与开发阻塞：两个调度器双向收发不意味着双方代码只能互相等完。先确定共同接口、数据和回调契约，再分别实现提供者/消费者，最后集成。遇到真正循环，先通过已确认的契约拆出可交付前置或明确标 blocked；不要按名字/端归属硬排顺序，不擅自重构业务打破循环。未知依赖影响的条目标 blocked，并说明解除条件，继续安排不依赖它的工作。

## 顺序和优先级
先按开发前置关系做拓扑排序，再在当前前置已满足的候选项中按用户优先级/P0、P1、P2 安排。P0 为主玩法闭环必需或阻塞项，P1 为本次核心与必须验收项，P2 为可延期增强，写明理由。优先级不能使消费者越过未满足的前置；用户明确执行顺序与实际依赖冲突时指出冲突，不默默忽略。

TODO 表按实际执行顺序排，增加“顺序”列，写清前置 ID；顺序号相同只用于互不依赖且确实可独立开展的工作。每个依赖项顺序号必须小于消费者。依赖不同但修改相同文件/共享状态的条目仍顺序执行；可独立工作不自动授权并行代理。

表前用一小段列清“先……再……最后……”及理由，按模块/阶段命名并链接相应规划。例如：先确定规则与事件信号契约 → 再完成波次/事件提供能力及规则执行者 → 再接入规则调度 → 最后集成、测试、文档与验收。这是按实际依赖调整的例子，不规定每个游戏都采用此顺序。

# 一份有序 TODO
默认在任务 README.md 的 `## TODO 与执行顺序` 维护一份表；篇幅大才拆到同任务 todo.md，入口仅链接并说明执行链，不复制状态。

| 顺序 | ID | 系统/目标 | 优先级及理由 | 前置 ID | 状态 | 接口/规划链接 | 验证与验收条件 | 证据 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |

ID 稳定不随排序变化；前置 ID 用逗号分隔，没有用“—”。每项有所属模块、具体交付目标、优先级及理由、前置、状态、规划/API 链接、可观察验证/验收门槛与真实证据。表前的执行链和表中排序必须一致，不另外维护第二份任务状态。

状态为 todo → doing → implemented → verified → accepted，另有 blocked/cancelled。implemented 仅表示实现完成；消费者可以开始的门槛按实际交付契约说明，例如“前置接口已核对”或“提供方模块验证通过”，不把一个勾选当成所有依赖都满足。没有达到门槛则不启动消费者。取消前置后必须调整依赖或标受影响项 blocked；实际模块关系变化时重新排序未完成项，保留 ID 和完成证据。

测试/验收可单列任务并依赖开发/集成工作；小项可在同一行记录，不机械扩成重复条目。工具检查重复/未知 ID、依赖循环、消费者排在前置之前或同顺序等错误；模块依赖是否完整、交付门槛是否满足仍需人工核对。

# 开发、测试、验收
- 开发：按已确认接口与职责实现；每次改动同步声明、契约注释、版本及文档映射，planned 转 implemented 的依据是对照真实实现。
- 测试：依据变更选择项目要求的构建、模块测试、配置导出检查、客户端/服务端集成和可见游戏行为验证。验证公开行为、生命周期和端间契约；可逆低影响改动可用适当检查，不机械新增镜像测试。真实游戏行为必要时使用项目规定的预览、运行日志、截图或复现场景。
- 验收：规划阶段先写可观察的 Given/When/Then 或明确步骤与预期结果；单系统检查后验证任务的跨系统主流程和本次范围内失败/边界路径。绑定代码版本、命令/场景、结果和证据链接。
只有必需 TODO、相关验证、系统文档/API 同步和整体验收均完成才报告整项完成。环境不能运行则记录未验证及缺少条件，不能标 verified/accepted。若用户要求人工验收，自动检查通过只标 verified，人工确认后再 accepted；不因流程人为增加未要求的审批。
