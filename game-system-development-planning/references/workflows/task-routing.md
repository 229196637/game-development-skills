# 统一入口与路由
每个开发任务以 docs/规划/<任务>/index.md 为独立入口；从这里读取当前任务详细需求、模块关系、TODO、优先级及测试验收。详细内容和所属模块规划均在该任务目录内保存，不散放在项目总索引。docs/index.md、docs/规划/index.md 或已有索引只链接任务，不作为任务执行入口。
游戏开发以 game-system-development-planning 组织任务，涉及配置时调用 game-excel-config，查阅/同步文档时调用 game-system-development-documentation；仅补文档的任务可以直接使用文档技能。按项目现有客户端、服务端、UI、测试技能处理实际领域，只有确实相关时加载。路由是职责划分，不自动授权多代理、创建聊天或并行写文件。

# 多系统任务
一个任务只维护一份总规划，位置 docs/规划/<任务>/index.md，连接该任务目录下各模块文件。详细保存任务背景、已确认需求、目标与预期结果、范围、约束、共享接口、依赖关系、优先级理由、TODO 和测试验收；过长的专题可拆为同目录 Markdown，并由任务入口链接。不同任务分别建文件夹，不将其模块规划混入同一目录。
| 系统 | client/server/shared | 提供接口 | 消费接口/上游依赖 | 规划与系统文档 |
| --- | --- | --- | --- | --- |
共享契约由明确的所有者维护；调用方链接该声明，不复制另一份签名。接口变化及时更新消费系统的关系、TODO 和验证范围。依赖循环先明确真实调用与状态所有权，再在规划中解决或标待确认，不盲目启动相互阻塞的实现。

# 优先级与开发顺序
用户指定优先级优先。否则 P0 是主玩法闭环必需或阻塞其他系统的工作，P1 是本次核心功能和必须验收项，P2 是可延后的增强；每项写明理由，不把未知业务重要性臆定为 P0。
顺序首先满足前置依赖，再在当前可开展项中按优先级安排。通常先确定公共契约/配置数据及关键边界，再完成提供者和消费者，最后集成；按真实依赖调整，不机械规定服务器永远先于客户端。
依赖不同但改相同文件或共享状态的工作不当作可独立并行；需要并行代理时遵守用户及项目授权。当前阻塞项说明依赖/缺失信息，继续不依赖它的授权工作。

# 一份 TODO
默认在任务 index.md 维护 TODO 表；只有篇幅大时拆为同任务 todo.md，由任务页链接。不要同时在各系统复制同一份状态。
每项有稳定 ID、所属系统、具体目标、优先级及理由、前置 TODO ID、状态、接口/规划链接、验证或验收条件、完成证据。粒度为可独立开发和检查的功能/契约，不拆成每行代码。
状态使用 todo → doing → implemented → verified → accepted；另有 blocked 和 cancelled。implemented 表示开发完成，verified 表示相关检查实际通过，accepted 表示对应验收条件满足。失败保留证据并回到需修复状态，不只勾掉待办。
多阶段工作可单列开发、集成、测试、验收任务并引用前置 ID；小任务可在同一行记录各阶段，不为仪式重复造条目。工作推进时同步 TODO、API 状态及 Markdown，状态不能只在聊天里维护。

# 开发、测试、验收
- 开发：按已确认接口与职责实现；每次改动同步声明、契约注释、版本及文档映射，planned 转 implemented 的依据是对照真实实现。
- 测试：依据变更选择项目要求的构建、模块测试、配置导出检查、客户端/服务端集成和可见游戏行为验证。验证公开行为、生命周期和端间契约；可逆低影响改动可用适当检查，不机械新增镜像测试。真实游戏行为必要时使用项目规定的预览、运行日志、截图或复现场景。
- 验收：规划阶段先写可观察的 Given/When/Then 或明确步骤与预期结果；单系统检查后验证任务的跨系统主流程和本次范围内失败/边界路径。绑定代码版本、命令/场景、结果和证据链接。
只有必需 TODO、相关验证、系统文档/API 同步和整体验收均完成才报告整项完成。环境不能运行则记录未验证及缺少条件，不能标 verified/accepted。若用户要求人工验收，自动检查通过只标 verified，人工确认后再 accepted；不因流程人为增加未要求的审批。
