# 需求研究与文档准备

## 直接调用规划

用户可以只调用游戏系统开发规划。开始先读取项目规范、需求与当前相关模块的架构/源码入口、已有文档和 API，研究实际职责、调用关系、生命周期、可复用能力及需要改动的边界。限定在需求涉及的代码与消费者，不全项目扫描；接口声明足够的纯 API 查询仍遵守文档技能的查阅规则。

把“已有实现”“本次拟新增/修改/删除”“未确认业务”区分清楚。已有框架已提供所需能力时，给出接口、调用契约与差距，沿用已确认复用选择；重写需要用户决定时再问，不替用户创造业务规则。没有现成实现时，用真实架构和已确认需求设计接口，不编造已实现能力。

## 调用文档能力

研究结论与已确认需求交给游戏系统开发文档，明确影响模块及设计态/现状态：

- 没有文档：生成需要的模块入口、同级目录架构、职责、公开函数 API 和确有需求的专题。
- 文档已有且适用：保留并核对相关部分，不为了流程重写整套资料。
- 文档不完整或需求改变：增补、修改受影响内容；实际已失效的类、API、专题或重复资料可以删除，修复模块/类索引、meta 文档依赖、API 映射与图内跳转。
- 尚未实现的拟议变更：写设计态资料；拟删除或替换代码不意味着当前正式 API 已消失，不能提前把正式文档改成未来事实。开发后再据实际差异同步。

文档能力只读相关代码并生成/维护文档，不实现业务、不建执行工单、不排序任务、不记录测试验收状态；文档自身仍按独立 Git 管理。删除之前核对范围、实际失效依据与引用，不删除 SDK/第三方资料或不相关模块。

## 再建立执行工单

文档/接口及需要的设计决定明确后，读取对应类 MD，建立与文档同相对层级、同文件名的工单，填写具体工作与验收标准，按依赖写清后续执行顺序。默认交付文档和完整工单后停止，不开展生产实现、不运行业务测试或验收。调用规划技能、给出开发需求和工单完成编写都不构成执行授权。只有用户明确要求执行本次工单时，才实现、测试、验收和同步文档；每一步记录保留真实状态与证据。

默认交付物中的 status 为 todo 或真实规划阻塞状态，任务项未勾选，测试/验收写未执行；可以校验文档格式、链接、依赖及工单内容，但不把这类校验写成业务实现或验收通过。
