# 规划流程
## 调查
优先从系统 Markdown 的映射查阅 client/<模块>/、server/<模块>/、shared/<模块>/ API，shared 是两端共享。已实现 API 足以回答且无过期或冲突时不扫描源码；缺失、不一致或需要确认边界时才查相关源码。
读取项目指令、文档和依赖，区分已有契约、拟定接口与待确认业务问题；保留既有职责和可复用接口。

## 已有框架能力选择
查阅 API 后先执行 [已有框架能力与重写选择](framework-reuse.md)：有现成能力就给准确接口、调用/生命周期细节及需求差距，再询问复用还是重写；选择未明确前不规划替代接口，既有选择沿用。

## 任务入口、TODO 与验收
先创建或更新 docs/规划/<任务>/index.md 作为本次开发入口，详细保存任务背景、已确认需求、目标、范围、约束和预期结果，按 [任务路由](task-routing.md) 列出系统依赖、优先级及理由、TODO 前置关系和开发/测试/验收条件。它路由到各系统文件；状态和证据随工作同步，不靠聊天承载进度。

## 规划范围与文件
每个任务保留自己的详细规划，在 docs/规划/<任务>/<模块>/ 中建立：
- architecture.md：目标文件夹、系统边界、端归属和依赖方向，必须画出该模块自己的依赖架构图及节点/API 映射。
- responsibilities.md：类/模块职责、状态所有者、生命周期、接口提供者。
- interfaces.md：接口目的、拟定原语言公开函数签名、参数/返回/异常及调用前提；直接链接对应 API 文件，不重复维护两份签名。
- relationships.md：调用方 → 提供方 → 使用接口、调用顺序、依赖关系、端间通信与共享边界。配合本模块架构图用表格说明关系，不展开内部实现。
- flows.md：必须绘制该模块主要入口的关键流程图，按真实需要增加跨端/异步时序图和生命周期状态图；明确接口、责任、条件、结果与必要分支，链接 TODO 和验收场景，不写具体算法或伪代码。详见 [模块图规范](module-diagrams.md)。
- config.md：有 Excel 配置需求时必须按游戏 Excel 配置表技能整理源工作簿/Sheet、完整字段字典及每字段必填注释（用途、单位、格式、约束、缺省与外键语义）、表头格式、端开关、类型/缺省与外键、导出结果/路径和读取接口映射，明确如何生成和校验，不只列字段名称。
- ui.md：模块需要 UI 时按 [UI 规范](ui.md) 单独规划并链接本模块 ui-preview.html 设计稿；明确逻辑执行端、对应模块代码目录及当前 UI 框架，任务入口路由 UI 实现/测试/验收。无 UI 不创建。
- verification.md：外部可观察的验收条件、测试与复现场景、跨系统集成条件，绑定总规划 TODO ID，不规划内部算法。

每文件只处理一个系统，任务 index.md 连接各系统与依赖。规划不要求 implementation.md，不写实现伪代码、算法步骤或函数体。

## 规划阶段就生成 API
使用项目实际语言，在 docs/规划/<任务>/api/client/<模块>/、server/<模块>/、shared/<模块>/ 中创建拟定公开函数声明；沿用已有接口，不将拟定签名冒充现有 API。
文件头 Status 写 planned；Source 注明拟定源码路径、尚未实现；CodeRevision 是规划所参考的代码基线而非实现版本；Verification 写仅完成契约设计、未实现验证。同文件包含已有和拟定函数时写 mixed，并在每个新增或修改中的函数注释标明 planned，原有已实现函数仍标 implemented。
任务入口和模块 interfaces.md 直接映射当前任务内的拟定 API；现状系统 Markdown 继续引用已经实现的正式 API，不用未实现提案覆盖当前契约。拟定行为用“计划/拟定”，不得声称实现已执行校验或会抛出特定异常。无已确认业务依据的契约留待确认，不猜测规则。
原语言格式、公开函数范围、版本注释与隔离遵循 game-system-development-documentation 的 API 规范。若另一技能不可用，按上述要求输出声明，不补造业务实现。

## 开发与 API 移交
开发阶段仍完善任务目录中的拟定 API；文件内所有函数核对实现后，由 game-system-development-documentation 移动到 docs/文档/api/<端>/<模块>/，移除原位置并同步任务/模块规划和系统 Markdown 的链接，保留一份当前声明。planned/mixed 文件继续留在任务目录，不提前移到正式文档。

## 开发阶段逐步完善
开发时使用同一套 API 文档，不另建一份“实现版”重复维护。每次实现或更改同步实际签名、函数契约注释、状态、源码和版本、系统 Markdown 映射及关系说明。只有对照实现核实的函数才由 planned 转为 implemented；部分完成的文件保持 mixed，未完成函数保持 planned。
开发阶段基于实际代码补充系统使用说明、初始化和释放约束、验证结果；变化同步回规划中的职责和调用关系。只有文件内所有接口均实现核对后才将文件 Status 标为 implemented，验证方式与结果单独记录，不以 implemented 代表测试已通过。
接口查询可直接查文档，但 planned 函数不能作为当前可调用接口。交付区分已实现和未实现接口、待确认项及两个 Git 仓库状态。
