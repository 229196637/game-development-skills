# 讨论与决策

## 开始
读取用户需求和相关系统策划、待确认记录及依赖；涉及已有行为时只读查阅相关资料/代码，不全项目扫描。没有系统策划时先整理明确目标，不创造完整玩法填空。

用简短问题讨论真正影响规则的选择：玩家目的、触发条件、输入/结果、消耗/奖励、失败与中断、跨系统影响。数值未知保留问题；需要举例时明确放在待确认候选中，不写成正式默认值。

## 记录与更新
每轮先更新已明确内容，再将未决定的问题写入独立待确认.md；用户希望晚点决定时可直接交付草案与问题入口，不强求当轮定稿。正文只链接问题，不复述候选。规则改变时核对受影响系统，原有规则在新决定明确前保持。

用户明确选择后，将规则及图表同步至策划正文，待确认表记录“已解决”、实际决定来源和正文链接。来源可为真实日期加用户原意摘要；没有真实消息 ID 时不编造。

## 衔接
独立讨论完成即停止。用户要求开发规划时，交给游戏系统开发规划读取策划与待确认记录；只阻塞依赖该决定的范围。技术架构、API、工单、实现和测试分别由既有技能负责，不自动进入执行。
