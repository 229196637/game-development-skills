# 策划文档约定

## 目录与 meta
```text
docs/策划/
├── README.md
└── <系统>/
    ├── README.md
    ├── 策划.md
    └── 待确认.md  # 按需
```

README 概括系统用途与资料入口。根 README 用“系统｜用途｜策划｜待确认”索引；系统 README 链接策划、相关系统和存在的待确认文件。大型系统可以增加主题 MD 和子文件夹；每目录有 README，策划.md 仍为系统正文入口并链接主题。

所有策划 MD（包括 README）使用精简 YAML meta：
```yaml
---
system: "背包系统"
updated: "2026-10-15 14:30:00 +08:00"
dependencies:
  - "../道具系统/策划.md"
---
```
根 README 的 system 用“策划索引”。dependencies 是相对当前文件的文档路径数组，无依赖用 []；记录真实文档/系统依赖，不只记录源码，不把所有导航链接都当依赖。无需 manifest、状态副本或全局编号表。

## 高效表达
| 内容 | 推荐表达 |
| --- | --- |
| 目标和玩家体验 | 一两句文字 |
| 触发、顺序、分支、结束 | 核心玩法流程图 |
| 条件、动作、结果、限制 | 核心规则表 |
| 数值配置需求 | 字段、含义、单位、用途；未知值进入待确认 |
| 系统交互 | 按需关系图，并链接其他系统策划 |

每系统至少一张 Mermaid flowchart/graph 和一张包含实际规则的表格，放在策划.md 或其直接链接的主题 MD。待确认表、目录索引表不能冒充核心规则表。使用模板的“核心流程”“规则”章节，复杂主题可沿用相同章节名以便工具检查。

图中节点简短，字号建议20px；超出阅读宽度就拆主流程/子流程，支持点击跳转。跨系统交互图有实际关系时才创建，不画装饰图。不在一张图塞入技术类和所有分支。不固定表格数量或填无关小节。

## 待确认.md
按稳定问题 ID（例如 Q-01）记录：
“问题｜候选方案｜影响｜状态｜决定及来源｜正文链接”。
状态只用“待确认”或“已解决”。候选无依据时写“待讨论”，不臆造用户偏好；解决后明确真实决定、来源与目标章节。没有问题时可不创建；已有解决记录保留。

正文可写“容量上限见待确认 Q-01”，但不能把未定容量写进确定规则或核心流程。讨论报告不混入正式技术文档，测试报告仍归 docs/测试。
